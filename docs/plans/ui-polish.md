# UI polish

An implementation plan for the approved explanation-block and diagram-control polish. This is a new branch of work, not a replacement for the earlier explanation-parts implementation plan.

## Goal

Make code and explanation diagrams recognisable framed reading blocks, and make diagram controls consistent without changing explanation data, drawing geometry, or existing map and finished-picture behavior.

## Specification

The authority is the following committed specifications at `f2fb22f`:

- [Explanation parts](../spec/explanation-parts.md).
- [Interaction and notifications](../spec/interaction.md).
- [Screen](../spec/screen.md).

The accepted implementation consists of 27 commits ending at `3d7f093`, followed by the specification commit. Its reported passing baseline is 139 Rust tests and 207 browser tests; these are previous verification results, not a new run or an acceptance quota. Re-establish them in step 1. The older [explanation-parts plan](explanation-parts.md) records historical decisions only: its native diagram scrolling, natural-scale dialog opening, Reset button and 0-key reset are superseded. Read current code and the above specifications for behavior.

## Approach and why

### Reuse decisions

Search was scoped to the current web components, `dom.js`, `pan-zoom.js`, stylesheet, strings, package manifest, browser fixtures and existing tests. No new dependency is needed.

| Independently decidable layer | Decision and grounds |
| --- | --- |
| Explanation transport, schema and geometry | Omit new work (ladder 1): all parts already exist. Keep Rust, SVG geometry, finite bounds and collision validation unchanged. |
| Local component state and surviving focus | Adopt codebase (2): `Component`, stable `data-focus`/scope keys, `CodeParts` registry and `KeyedList` already serve this purpose. Add an analogous small diagram registry only because inline and dialog views now need surviving local transforms. |
| Dialog arbitration, inert background and opener restoration | Adopt codebase (2): `ui.dialog`, `DialogLayer`, `holdFocusInDialog`, `restoreExplanationFocus` and `explanation-ready`. Do not introduce a second dialog manager or replace this with a new modal framework. |
| Mouse/wheel transform and fit mathematics | Adopt codebase (2): `PanZoom.zoomAt`, `zoomBy`, `fitView` and callbacks already provide pointer-centred transforms and fit-below-manual-minimum behavior. |
| Inline touch routing | Extend codebase plus platform (2/4): existing page-mode Pointer Events do not guarantee second-finger takeover after native scrolling cancels pointers. Use the explicit, surface-local protocol in J3, not a gesture library. |
| Code copy and manual selection | Adopt codebase (2): `CodePart.copy`, Clipboard API and Range/Selection already implement exact-body copying and readable failure. Never copy the mock's hidden fallback API. |
| Frame, icons and compact controls | Adopt CSS tokens, DOM and SVG facilities (2/4); build small local presentation helpers. `header.js` has private theme SVG construction, not a reusable operation-icon set; no installed icon/toolbar library exists. Local fixed paths are sufficient and introduce no format contract. |
| Browser and Rust verification | Adopt codebase (2): Playwright fixture launches a real isolated topic server; existing suites and workspace gates already cover unrelated behavior. Use an approved external browser config rather than change build scripts. |

The two viewports own separate transforms. The application owns only which dialog is open and the existing stable opener identity. As with each card/provisional row's `CodeParts`, each reading region owns its inline diagram registry; `question-parts.js` and `thread.js` receive that registry from their owning card/provisional component. The explanation dialog body owns its separate retained viewport component, cached by DialogLayer for the open identity/content, not a transform copied into `ui` or saved topic state. Top-level app integration only supplies dialog view data and mediates open/close/focus events. Controls receive current scale and callbacks, not topic data; they neither mutate answers nor own another component's transform. Rendering remains read-only; connect observers and input listeners in component lifecycle code, and release them on removal. If retained draw functions still return plain elements, extract only the lifecycle boundary needed by the present second caller; do not invent a general rendering framework.

### Provisional answers and approval judgment points

These concrete answers make the plan recoverable without the visual mock or the conversation. The person approves the actual plan bytes, including these points; exact CSS values are proposals, not new specification boundaries.

**J1 — Visual tokens and icons.** Reuse `--sheet` for diagram bodies, `--sheet-sunk` for code bodies and block/toolbar headers, `--ink` for body text, `--muted` for metadata/icons, `--line` for a restrained 1px frame, `--accent` for focus, and `--radius-small` for controls. Start block radius at 8px, header padding at 8px 12px, metadata gap at 8px, body code padding at 12px 16px, and block separation at 12px. Headers have a 44px minimum rather than a fixed height: metadata wraps and the right operation keeps its own 36px square. Use 18px local stroke icons, 24-unit viewBox, stroke width 1.65, round joins/caps and `currentColor`; no external font, asset or copied library paths. Suggested original paths: minus `M5 12H19`; plus adds `M12 5V19`; whole-fit `M9 4H4V9 M15 4H20V9 M4 15V20H9 M20 15V20H15`; enlarge `M14 4H20V10 M20 4L13 11 M10 20H4V14 M4 20L11 13`; close `M6 6L18 18 M18 6L6 18`; move `M12 3V21 M3 12H21 M9 6L12 3L15 6 M9 18L12 21L15 18 M6 9L3 12L6 15 M18 9L21 12L18 15`; copy uses two offset outlined rectangles, and success a check `M5 12L10 17L19 7`. SVGs are decorative (`aria-hidden`, not focusable); each containing native button has its translated accessible name and tooltip. Keep a visible 3px focus outline with 3px offset without clipping it. Percentage is visible text, not an icon or editable value. Body text remains 0.875rem at the 16px baseline, not a width-responsive font.

The mock reported a light code-type color contrast of 4.11:1. Do not reproduce its syntax palette; syntax coloring is unnecessary. Existing palette math gives body `--ink` on `--sheet-sunk` 14.656:1 light and 14.346:1 dark; metadata `--muted` gives 4.934:1 and 6.685:1; accent gives 8.178:1 and 8.404:1. These figures use linearised sRGB relative luminance and `(Lhigh+0.05)/(Llow+0.05)`, not a whole-site accessibility certification. Test actual computed foreground/background pairs if styling changes them. Why: avoid an unrelated palette rewrite while fixing the mock's readability risk. Overturn if: the person requests another density, icon outline or palette after seeing both themes; retain readable metadata, labels and focus and remeasure changed pairs.

**J2 — Geometry and view ownership.** Read validated natural width/height from the successful SVG result (`width`, `height`, `viewBox` already emitted by `drawing.finish`), never from its transformed screen bounds. Allow an interface-only ready/failure callback in `explanation-diagram.js` to carry this result to its two viewport callers; do not edit geometry producers/validators. Inline starts at `{x:0,y:0,k:1}`; its SVG already contains drawing margins. The viewport has full available width and intrinsic natural height capped by `min(22.5rem,50vh)`, with no arbitrary minimum for short figures. Overflow is clipped, not native-scrollable; keep the entire SVG mounted. Put a persistent, wrapping hint below the viewport, outside the pan surface and controls, explaining hidden content and enlargement. The hint is not an overlay over labels.

Whole-fit in explanation views has **no positive minimum scale**: the existing shared 0.01 fit floor cannot contain every valid 8192-unit canvas in a small positive viewport. Localise the exception in an explanation-only fit helper in `explanation-viewport.js`; leave `PanZoom.fit`/`fitView` and all map/finished-picture callers' 0.01 floor unchanged. For measured viewport width W and height H, defer fit whenever either is nonfinite or nonpositive: retain the last valid transform (the natural initial transform if no fit has succeeded), keep the fit request pending, and retry after successful measurement and a positive ResizeObserver result. Do not manufacture a minimum viewport size, zero scale, or clamped partial fit.

For positive W/H and validated positive canvas dimensions, start with desired outer fit padding 12 CSS pixels per axis. Cap each side to one quarter of that axis: pX = min(12,W/4), pY = min(12,H/4). Thus availableW = W−2pX and availableH = H−2pY are always positive even when the viewport is smaller than the desired padding. Compute k = min(1,availableW/canvasW,availableH/canvasH), with no 0.01 floor, and centre using x = (W−canvasW*k)/2, y = (H−canvasH*k)/2. Canvas dimensions include the renderer's own margins; do not remove those or substitute transformed drawing bounds. Apply this exact rule to dialog opening, whole, focused 0 and fitted-mode resize/revalidation, including a 64px viewport with an 8192-unit canvas. Fit may produce an arbitrarily small positive scale; zero-size deferral is not a successful fit.

Keep the existing manual transform rule unchanged: upper clamp 3, ordinary lower clamp 0.2, and the existing fit-below-minimum exception `min(0.2,currentScale)` (the gesture's starting scale for pinch). Therefore a fit at 0.007 is retained; a + button multiplies it by 1.2 to 0.0084 rather than jumping to 0.2, and a − button below 0.2 clamps at its current scale rather than enlarging it or forcing a jump. Once the manual view reaches 0.2, the ordinary 0.2–3 clamp applies. Keep 1.2 button/key zoom, 40 CSS-pixel directional steps and the existing wheel factor `exp(-deltaY*0.0015)`; do not add a new zoom factor, change map/finished clamps or silently normalise a tiny fit on the next input. Dialog initially fits after successful async measurement and positive viewport size, and stays fitted across resize/revalidation until manual movement/zoom. Whole re-enters that fitted mode; 0 invokes the same action without moving focus. Inline initially stays natural across resize; an explicit whole action enters fitted mode until manual movement/zoom. Views retain local transforms across unrelated replies and language changes for the same identity/content; changing part content replaces its view state. Opening a dialog never overwrites inline state. Why: preserve genuine whole containment for all valid canvases without inventing a supported minimum viewport, and keep natural initial inline reading distinct from voluntary fit. Overturn if: the person prefers fit to enlarge small diagrams above natural size, different padding/resize policy or inline starting alignment. A supported viewport minimum or permission to clip after whole would require a new specification revision, not an implementer's floor choice; no automatic initial inline shrinking or map/finished policy change is permitted.

**J3 — A supported inline touch protocol, not assumed native takeover.** Existing `PanZoom` page mode ignores one touch but CSS `touch-action:pan-y` lets the browser start native scrolling and issue `pointercancel`; changing touch-action on the second contact cannot take back that gesture. For new explanation inline surfaces only, declare a distinct opt-in input policy with `touch-action:none` fixed before contact, Pointer Events and capture of tracked touch contacts. Route a single contact's vertical delta to the page's scrolling element using `scrollBy`, with the same direction as normal touch page reading; its diagram transform does not move. The page currently has one scrolling document, not a nested reading scroller. Rebase positions after every movement. Two contacts switch to custom midpoint translation and distance-ratio zoom around that midpoint, reusing PanZoom's math; neither changes document scroll. Rebase when entering or leaving the two-contact state so a lift cannot jump the page or diagram. A surviving single contact resumes page movement from its current position, not its original down position. Third and further contacts suspend movement until at most two remain, then rebase. On `pointercancel`, lost capture, removal, hidden view or dialog replacement, discard the active gesture, release captures and commit only the last valid view; no stale contact survives. Track starts on the diagram surface, not header/menu/code; a stationary press does not move anything. Mouse keeps the existing 4px drag threshold, left button and scale-preserving pan. No document-level nonpassive touch/wheel listener, global selection suppression or global `preventDefault` is allowed.

This protocol provides page reading rather than native one-finger inertia; it deliberately avoids an impossible native-scroll-to-custom-pointer takeover. No synthetic inertia is added. Browser page pinch over the diagram belongs to diagram zoom; outside it, native page pinch/text zoom remain untouched. Existing map, finished-picture and dialog touch policies remain unchanged; the new opt-in policy must not silently fix or rewrite their old page mode. Automated trusted touch sequences can prove the chosen routing in the approved Chromium but cannot prove real-device ergonomics. Why: both approved inline touch operations need surviving contacts, which the old native path cannot promise. Overturn if: the person requires native momentum/bounce or native one-finger scrolling specifically over inline diagrams. If real-device checks cannot provide both page reading and two-finger pan/pinch with this local protocol, stop: do not drop the two-finger operation, switch one finger to diagram pan, or silently use `pan-y`. A newly discovered nested scrolling reading surface also requires handback rather than a global scroll interceptor.

**J4 — Shared presentation, not shared behavior.** Add one compact zoom group in the order minus / current percentage / whole / plus. It accepts caller callbacks; map and finished-picture keep their current 1.25 factor, fit maximum and initial/reset/resize policies. Only explanation views get a separate compact Move menu. Use a native button with `aria-expanded`/`aria-controls` and a labelled, nonmodal popover group of four direction buttons: Tab reaches each, Enter/Space activate, Escape closes it and restores the trigger. Do not declare ARIA menu roles unless implementing their complete arrow-key navigation. Close the popover on outside activation or when the surface takes focus; it is local view state, not another `ui.dialog`. The explanation surface itself retains arrows, + and −, with 0 changed to whole. Keep stable action/focus attributes for map/finished callers; add no movement menu or new shortcut there. Put inline whole and the Move trigger in a small separate control strip, not over the drawing. Diagram labels may use `user-select:none` throughout the interactive surface; code, failure source and map detail text remain selectable, and map node click/tap/Enter/Space still open information. Why: share visual roles without changing ownership or existing input contracts. Overturn if: the person prefers another equivalent keyboard-accessible popover layout or drag-only selection suppression; do not add the forbidden 100%, undo or comparison selector.

**J5 — Flexible explanation dialog.** Start at width `min(92vw,76rem)`, maximum height `calc(100dvh - 2rem)` (provide a `100vh` fallback), and a preferred height of that available height. Use a flex column with wrapping title/role/header and toolbar and a `flex:1;min-height:0;min-width:0` clipped drawing viewport. On very narrow/short screens reduce outer margin to 8px and padding to 12px, preserving all controls and focus outlines. No fixed 65vh inner diagram plus scrolling modal body. Place the close icon at the upper right in the existing DialogLayer; limit its special layout to diagram dialogs, preserving confirmation/decision dialogs. Normal wheel is not diagram zoom or pan; do not add a background-scroll lock or wheel cancellation beyond existing modal/inert behavior. Failure replaces the viewport content with readable cause/source, not a clipped unselectable transformed pre; source may use its existing bounded overflow. Why: allocate the remaining space to the diagram rather than nested scrolling frames. Overturn if: the person prefers a less dominant modal size after inspecting short and narrow windows. Failure/source readability, visible controls, focus containment and genuine whole-fit stay mandatory.
