# 起動と往復と記録

shoryo は手元で動く小さな Web サーバー。議題ひとつにつき 1 つ起動し、ブラウザの画面と LLM の間で、ラウンド・答え・聞き返しを受け渡す。
議題の状態は shoryo のデータを正本にし、壁打ちが終わったあともそのデータを手元に残す。
画面の振る舞いは [画面](screen.md) にある。LLM 側の使い方は [shoryo skill](skill.md) にある。

用語は [CONTEXT.md](../../CONTEXT.md) に従う。

## 起動

### 議題と起動

shoryo は、議題を指定して起動する。1 回の起動で扱う議題はひとつだけ。
議題は「リポジトリのトップのパス」と「議題名」の組で見分ける。リポジトリの外で起動したときは、起動した場所のパスを使う。

同じ議題がすでに起動しているときは、2 つ目を起動せずに理由を出して終わる。
データがある議題を指定して起動すると、続きから再開する。

成功条件: 同じ議題を 2 回起動すると、2 回目は理由を出して終わる。止めたあと同じ議題で起動すると、過去のラウンドと送る前の状態が戻る。
反例: 同じ議題で 2 つのサーバーが動き、データを書き合う。
確かめ方: 往復のテスト。

### 出力

起動すると、画面の URL を出す。ラウンドを出すコマンドは、「第 N ラウンドを画面に出した」と画面の URL を出す。
問いの本文は出さない。警告とエラーは、これとは別に出してよい。

ポートは起動のたびに空いているものを使う。`--port` で固定できる。

成功条件: ラウンドを出しても、出力に問いや選択肢が含まれない。
反例: 出力に問いや選択肢が流れる。
確かめ方: 往復のテスト。

### 待ち受け先

既定では 127.0.0.1 だけで待ち受ける。`--bind` で待ち受け先を変えられる。
127.0.0.1 以外で待ち受けるときは、平文の HTTP で公開されることを警告に出す。

成功条件: 既定では、同じ PC 以外から開けない。`--bind` で 127.0.0.1 以外を指定すると、警告が出る。
反例: 既定で LAN から開ける。
確かめ方: 往復のテスト。

### 開き直し

ブラウザを閉じても、同じ URL を開き直せば続きから使える。
ブラウザのタブを 2 つ開いたときは、どちらにも同じ状態を出す。

成功条件: ラウンドの途中でブラウザを閉じて開き直すと、選んでいた答えと聞き返しが元のまま出る。
反例: 開き直すと、答え欄が推奨に戻る。
確かめ方: 往復のテスト。

## 設定ファイル

ユーザーごとの設定を、設定ファイル 1 つに持つ。置き場所はユーザーごとの設定置き場（例: Linux では `~/.config/shoryo/config.toml`。`XDG_CONFIG_HOME` に従う）。議題のデータとは別に置く。

設定ファイルに持つのは、画面の言語（`en` または `ja`）とテーマ（OS に合わせる・ライト・ダーク）。
画面で言語やテーマを切り替えると、shoryo が設定ファイルに書き込む。書き込みは、議題のデータと同じく一度に置き換える形で行う。
設定ファイルが読めない、または中身がおかしいときは、警告を出して既定の設定（英語・OS に合わせる）で起動する。壊れたファイルは書き換えず、画面で切り替えてもファイルには書かない（画面には読めないことを知らせる）。
動いているサーバーは、画面が開かれたときに設定ファイルを読む。ファイルの変更を見張りはしない。

言語で切り替わるのは画面の文言だけ。起動やラウンドの出力、コマンドのエラーは英語のまま。

成功条件: 画面で ja に切り替えると設定ファイルに書かれ、起動し直しても ja で出る。中身のおかしい設定ファイルがあっても起動でき、そのファイルは変わらない。
反例: 設定ファイルが壊れていると起動できない。切り替えると議題のデータに好みが書かれる。
確かめ方: 往復のテスト。

## 往復

LLM は、次のコマンドで画面とやり取りする。

| コマンド | すること |
|---|---|
| ラウンドを出す | 次のラウンド、更新した記録、完成図、議題の題名とそもそもの議題を渡す |
| 待つ | 画面で出来事が起きるまで待ち、起きた出来事を返す |
| 返す | 聞き返しへの返事を渡す |
| 終える | 議題を終える |
| 結果を渡す | 議題のデータ全体を出す |

LLM が渡すのは構造化されたデータだけ。HTML は書かない。画面がデータから描く。

### ラウンドを出す

ラウンドを出すコマンドは、受け取る前に中身を確かめる。次のどれかに当たれば、受け取らずに理由を返す。

- 推奨がちょうど 1 つでない問いがある
- 「この答えだと」がない選択肢がある
- 前提に、記録にない決まったことを指している
- 前のラウンドがまだ送られていない

成功条件: 推奨が 2 つある問いを含むラウンドを出すと、理由が返り、画面は変わらない。
反例: 推奨のない問いが画面に出て、答え欄の初期値が決まらない。
確かめ方: 往復のテスト。

### 待つ

待つコマンドは、画面で出来事が起きるまで戻らない。待つ時間には上限を指定でき、上限を過ぎたら、出来事なしで戻る。
返す出来事は次のとおり。

- 聞き返し（どの問いへの、どのやり取りの続きか）
- まとめて送った答え
- 見直したい、と見直したいをやめたこと
- 仕分けの入れ替え

出来事には識別子を付ける。LLM が待っていない間に起きた出来事も、消さずに取っておく。
待つコマンドは、受け取り済みと示されていない出来事をすべて返す。LLM は、次に待つコマンドを出すとき、受け取った出来事の識別子を渡す。受け取り済みと示された出来事は、もう返さない。

成功条件: 待つコマンドを出していない間に聞き返しと送信をして、そのあと待つと、両方を受け取れる。受け取り済みを示さずに待ち直すと、同じ出来事がまた返る。
反例: 待っていない間の送信が消える。待つコマンドが戻った直後に LLM が止まると、出来事が失われる。
確かめ方: 往復のテスト。

### 返す

返すコマンドは、聞き返しの識別子を指定して返事を渡す。返事には図を含められる。
渡した返事は、開いている画面にすぐ出る。送ったあとのラウンドへの返事も受け付けて、そのラウンドの記録に残す。

成功条件: 返すコマンドが終わると、画面を操作しなくても、該当のカードに返事が出る。
反例: 読み込み直さないと返事が出ない。
確かめ方: 往復のテスト。

### 終える

終えるコマンドは、ワークフローが承認まで終えたときに出す。最後のラウンドを送っただけでは、議題は終わらない。
送られていないラウンドがあるときは、終えるコマンドは理由を返して断る。
終えると、画面は「壁打ちは終わった」状態になり、答え・聞き返し・見直したい・仕分けの入れ替えは使えなくなる。過去のラウンド、地図、完成図、決まったことは見られる。
終えた時点で返事待ちだった聞き返しには、「返事なし」と出す。
終えたあとは、待つコマンドと返すコマンドを断る。ラウンドを出すコマンドは受け付け、その議題を再開する。レビューや仕様の手直しのために、同じ議題を続けられる。

成功条件: 終えたあとの画面では送れない。終えたあとにラウンドを出すと、その議題で答えられるようになる。
反例: 最後のラウンドを送ったら議題が終わり、レビューの結果を同じ議題に足せない。終えたらデータが消える。
確かめ方: 往復のテスト。

### 結果を渡す

結果を渡すコマンドは、議題のデータ全体を出す。ワークフローは、これを使って仕様を書く。議題を終えたあとでも使える。

成功条件: 終えたあとでも、議題のデータ全体を読み出せる。
反例: 読み出すには画面を開くしかない。
確かめ方: 往復のテスト。

## 状態データ

議題の状態は、議題ごとに JSON ファイル 1 つで持つ。これが議題の状態の正本になる。
問い・決まったこと・聞き返し・出来事には、議題の中で変わらない識別子を付ける。前提などの参照は、この識別子で指す。

データには次のものを入れる。

- **議題**: 題名、そもそもの議題（本人の言葉）、終えたかどうか。題名とそもそもの議題は、LLM が最初のラウンドで渡し、あとのラウンドで直せる
- **ラウンド**: 番号、話題、レビューのラウンドかどうか、直したこと（何を直したか、直した決まったことと前と後）、問い、見直しの結論、確かめ済みの点
- **問い**: 文、区分（今の区分。人が入れ替えたらそれ）、なぜ今、前提にしている決まったこと、前提知識、選択肢、先送りされた問いを聞き直したものなら元の問い
- **選択肢**: 文、説明、推奨かどうか、この答えだと
- **答え**: 選んだ選択肢、補足、先送りのラベル、判子（本人が押した・代決のまま）
- **聞き返し**: どの問いへのものか、聞いたこと、返事、図、どのやり取りの続きか
- **記録**: 6 種類の記録と見直し中のもの
  - 決まったこと: 短い名前、全文、どの問い（直したことで決まったものは、どのラウンドの直したこと）で決まったか。改めたときは、前の中身を改めたことに残し、どのラウンドの時点の中身かを描き直せるようにする
  - 作らないもの
  - 未決: 決める人
  - 任せたこと: 理由
  - 見送った案: 理由と、どの問いで見送ったか
  - 改めたこと: どの決まったことを、何から何へ
  - 見直し中のもの
- **完成図**: 最新のもの
- **送る前の状態**: 選んでいる答え、補足、先送りのラベル、判子

送る前の状態は、画面で操作するたびに保存する。

見直し中は、人が画面で付けたり外したりする。ラウンドを出すコマンドで渡す記録の中の見直し中は使わず、画面で付いたものを保つ。
見直し中が外れるのは次のときだけ。

- 人が「見直したい」をやめたとき
- LLM がラウンドで、その決まったことの見直しの結論を渡したとき（中身を改めた、またはそのままでいい）

見直しの目印も、LLM がラウンドで「そのままでいい」と確かめた点を渡したときに外れる。

成功条件: データだけから、過去のどのラウンドの画面も答えたときの中身で描き直せる。ラウンドの途中で shoryo を止めて起動し直すと、送る前の先送りのラベルも元のまま戻る。
反例: 聞き返しの返事がデータに残らず、過去のラウンドで消える。LLM がラウンドを出したら、人が付けた見直し中が消える。
確かめ方: 往復のテスト。

## 記録の置き場所と寿命

データは、ユーザーごとのデータ置き場（例: Linux では `~/.local/share/shoryo/`）に置き、リポジトリと議題ごとに分ける。
リポジトリの中には置かない。

shoryo はデータを自動では消さない。仕様が承認されたあとも残す。消すのは本人が決めたときだけで、本人がその議題のデータを消す。

成功条件: 終えたあともデータが残り、同じ議題で起動し直すと過去のラウンドが見られる。リポジトリの作業ツリーにファイルが増えない。
反例: 承認後や終えたあとに、データが消える。データがリポジトリの中にできる。
確かめ方: 往復のテスト。

## 作り方と配り方

Rust で作り、画面のファイルも含めたバイナリ 1 つにする。
GitHub のリリースに置き、mise の github バックエンドで入れられるようにする。

成功条件: バイナリ 1 つだけで、画面も含めて動く。mise で入れられる。
反例: 画面のファイルを別に置かないと動かない。
確かめ方: 人がリリースを mise で入れて確かめる。

## 作らないもの

- 推奨と答えた割合などを数える仕組み。
- 今の brainstorm（ba0918・kotowari）の書き換え。それぞれのリポジトリの別作業にする。
- 仕様を書くこと、承認をもらうこと。これはワークフローの仕事。

## 見送った案

- claude.ai の Artifact で画面を出す: 手元の LLM に答えを返せるかが確認できていない。すでに動いている kemi と同じ形を選んだ。
- 画面は見るだけにして、答えはターミナルで打つ: 問いの本文がターミナルに流れ続ける。
- 承認したら記録を消す: 説明や聞き返しが消えて、あとで認識のズレをたどれない。
- 記録をリポジトリに入れる: 会話の生の記録が履歴に残る。
- 最後のラウンドを送ったら議題を終える: レビューの結果を同じ議題に足せない。

## 任せたこと

- JSON の項目名と細かい形: 何を持つかは [状態データ](#状態データ) で決まっていて、名前の付け方で振る舞いは変わらない。
- コマンドの名前と引数: どのコマンドがあり、何をするかは [往復](#往復) で決まっている。
