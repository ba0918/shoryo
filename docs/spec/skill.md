# shoryo skill

shoryo skill は、LLM が shoryo を使って壁打ちのラウンドを進めるための手順書。shoryo のリポジトリに、ツール本体と一緒に置く。
grill-me 方式で問いを出し尽くすこと自体は変えない。変えるのは、人の頭に乗る分。そのために、問いを仕分け、つながりと最終形を画面で見せる。
画面の振る舞いは [画面](screen.md)、コマンドとデータは [起動と往復と記録](server.md) にある。

用語は [CONTEXT.md](../../CONTEXT.md) に従う。

## 受け持ち

shoryo skill を呼ぶのは、壁打ちを進めるワークフロー（ba0918 や kotowari の brainstorm など）。受け持ちは次のように分ける。

- **shoryo skill**: ラウンドを shoryo の形で書くこと、問いの仕分け、質問への返事、先送りと見直しへの対応、完成図、記録を shoryo のデータに書くこと。
- **ワークフロー**: 問いの木をどう進めるか、いつ終えるか、結果のデータからどう仕様を書き、どう承認をもらうか。

ワークフローから shoryo skill を呼ぶように書き換えるのは、それぞれのワークフローのリポジトリの作業。
書き換える前でも、人が「この壁打ちは shoryo でやって」と頼めば使い始められる。
shoryo を使っている議題では、記録を shoryo のデータにだけ書く。ワークフローの進捗ファイルに同じ記録を持たない。

成功条件: 今の brainstorm を書き換えないまま、人が頼むと shoryo の画面で壁打ちが進み、記録が shoryo のデータにだけ残る。
反例: shoryo skill が仕様の書き方や置き場所を決めている。同じ記録が、進捗ファイルと shoryo のデータの両方にある。
確かめ方: 人が実物の壁打ちで確かめる。

## 会話に問いを書かない

ラウンドを出したら、会話には「第 N ラウンドを画面に出した」と画面の URL だけを書く。問い、選択肢、推奨、記録の中身は会話に書かない。
ラウンドは構造化されたデータで渡し、HTML は書かない。

成功条件: ラウンドを出したあとの LLM の会話の発言が、1 行の案内だけになる。
反例: 画面に出した問いを、会話にも書き並べる。
確かめ方: 人が実物の壁打ちで確かめる。

## 問いの仕分け

問いを「人が決める」と「仮決め」に分ける。基準は「あとから変えたら高くつくか」。

- **人が決める**: 目的、方針、使う人から見える振る舞い、トレードオフに関わる問い。あとで変えると、ほかの決まったことまで崩れるもの。
- **仮決め**: 名前や細かい既定値など、どれを選んでも決まった振る舞いが変わらず、あとで安く直せるもの。

振る舞いや設計に強く影響する問いは、仮決めに入れない。仮決めは代決の判子付きで出るので、紛れると見ないまま送られうる。迷ったら人が決める問いに入れる。

人が画面で区分を入れ替えたら、その問いはその区分で扱う。聞き直しや問い直しで同じ問いを出し直すときも、入れ替えた区分のまま出す。
入れ替えは、似た問いをどう仕分けるかの手がかりにもする。

仮決めも、送られて初めて答えになる。返事がないことを同意として扱わない。

成功条件: 名前や既定値の問いが仮決めに入り、方針の問いが人が決めるに入る。入れ替えた問いを出し直すと、入れ替えた区分で出る。
反例: すべての問いが同じ区分に入る。送られていない仮決めを、決まったことに書く。
確かめ方: 人が実物の壁打ちで確かめる。

## 問いの書き方

問いごとに次のものを書く。

- 問いの文
- なぜ今決めるか（1 行）
- 前提にしている決まったこと
- 前提知識（その問いを読むのに要る用語や背景）
- 選択肢。推奨はちょうど 1 つ。選択肢ごとに、説明と「この答えだと」を書く。

決まったことには、前提の行と地図で使う短い名前を付ける。ラウンドには、地図の列の見出しに使う話題を付ける。

成功条件: どの問いにも推奨がちょうど 1 つあり、すべての選択肢に「この答えだと」がある。
反例: 推奨のない問いがある。前提を番号だけで書く。
確かめ方: ラウンドを出すコマンドの検査（[ラウンドを出す](server.md#ラウンドを出す)）。

## 質問への返事

質問には、その問いについて返事をする。説明は [表現の選び方](#説明の表現を選ぶ) に従い、[説明パーツ](explanation-parts.md#対象と読み順) の列で書く。
返事を書いても、出したラウンドの問いの文は書き換えない。聞き方が悪かったとわかったら、返事の中で言い換えを示す。

成功条件: 返事は聞かれた問いのカードに出て、問いの文は出したときのまま残る。
反例: 質問を受けて、出したラウンドの問いの文を差し替える。
確かめ方: 人が実物の壁打ちで確かめる。

## 説明の表現を選ぶ

前提知識、選択肢の詳細説明、返事に必要な構造に合わせ、判断に必要な最小の表現とパーツ数を選ぶ。
短い文章で十分なら文章だけにし、条件があるという理由だけで毎回図やコードを付けない。
同じ内容の全文を文章とパーツに重ねず、導入や注意点が必要なら読み順に並べる。
使う種類、立場、表示と入力の契約は [説明パーツ](explanation-parts.md) に従う。

スキルには選ぶ例と避ける例を持たせる。

- 条件と処理の対応を読む必要があるなら、疑似コードを使う。通知先など未決の細部は埋めない。
- 登場人物間の往復と順序が判断に必要なら、シーケンス図を使う。順序だけで分かる説明に厳密な実行時間を追加しない。
- 条件ごとの枝、合流、戻りを追う必要があるなら、フローチャートを使う。単純な一本道を図の数を増やすためだけに描かない。
- 実コード自体を読む必要があるなら、実コードを表示する。確認していない実装を確認済みの現状として出さない。
- 一文で違いが分かるなら文章だけにする。パーツの種類や数を埋めるために追加しない。

成功条件: 読者が何を判断するための表現か説明でき、文章だけで済む例では図を付けず、順序や分岐が必要な例では対応する表現で理解を助ける。
反例: すべての条件に疑似コードを付ける。本人が要求するまで適切な表現を選ばない。文章と図で説明全文を繰り返す。
確かめ方: 人が問い、選択肢、返事と選んだ表現を見比べ、判断に必要な構造と余分な説明の有無を確認する。スキルの文面の完全一致を自動テストで固定しない。

## 説明の意味を確かめる

図やコードを出す前に毎回、問い、選択肢、既存の合意との整合、分岐の条件、矢印の向き、順序、立場、説明の重複を確かめる。
判断に必要な未決の細部は問いにし、例や案の中で勝手に埋めない。
案や例に含まれる細部を、問いに押された判子だけで独立した合意として記録しない。
確認済みの現状は、実際に確認した内容に限る。

入力エラーや表示失敗の指摘を受けたら、原因に応じて修正、小さく分割、文章やコードへの変更を行う。
上限超過では内容を黙って落とすのではなく説明を分割する（[受理と保存](server.md#説明パーツの受理と保存)）。
試せる場合は表示確認を勧めるが、毎回のブラウザ撮影やモデル評価を必須にしない。
見ていない図を表示確認済みとは言わない。
表示の成功だけを意味の正しさの根拠にしない。

成功条件: 条件や順序が合意と対応し、未決の細部を合意として扱わない。失敗の指摘に対処し、意味の確認と実際の表示確認の有無を区別できる。
反例: 予算の条件を説明する例に未決の通知先を入れ、そのまま決まったことにする。表示していない図を表示確認済みとする。失敗を無視して続ける。
確かめ方: 人が元の問い、回答、合意、パーツと記録を見比べる。失敗を指摘した際の修正と、確認した範囲の報告も確認する。CLI の構文検査や文面一致だけでは合格にしない。

## 待ち方

ラウンドを出したら、送られるまで待つコマンドを出し続ける。上限を過ぎて出来事なしで戻ったら、待ち直す。
出来事ごとに次のようにする。

- **質問**: 届いた順に返事をして、待ち直す。
- **見直す、見直しをやめたこと、仕分けの入れ替え**: 次のラウンドのために覚えて、待ち直す。会話には戻らない。
- **まとめて送った答え**: 記録を更新して、次のラウンドを出す。

成功条件: ラウンドの途中で見直すを押しても、そのあとの質問に返事が来る。
反例: 見直すを受け取った時点で待つのをやめ、残りの質問に返事が来ない。
確かめ方: 人が実物の壁打ちで確かめる。

## 送られた答えの扱い

まとめて送られた答えは、推奨のままのものも、代決のまま送られた仮決めも含めて、すべて答えとして扱う。先送りのラベルが付いた問いは除く。
答えから記録を更新し、次のラウンドを出す。記録は、決まったこと、作らないもの、未決、任せたこと、見送った案、改めたことの 6 つ。

成功条件: 次のラウンドを出すときには、前のラウンドの答えが記録に入っている。
反例: 答えた問いが、記録で未決のまま残る。
確かめ方: 人が実物の壁打ちで確かめる。

### 先送りされた問いの聞き直し

先送りのラベルが付いた問いは、決まらずに残す。次のラウンドで、聞き方を変えて出し直す。たとえば、問いを小さく分ける、具体的な場面にする、前提知識を足す。出し直した問いには、元の問いを記録する。

成功条件: 先送りされた問いが、次のラウンドで違う聞き方で出る。
反例: 同じ文のまま出し直す。推奨で決めてしまう。
確かめ方: 人が実物の壁打ちで確かめる。

### 見直しの問い直し

「見直す」が届いた決まったことは、次のラウンドで問い直す。
答えが変わったら、元の決まったことを新しい中身に置き換え、古い中身を改めたこととして記録する。
答えが変わらなかったら、「そのままでいい」を見直しの結論として渡す。どちらの場合も、ラウンドで見直しの結論を渡す。
答えが変わったら、その決まったことを直接前提にしている問いと決まったことを、次のラウンドで「そのままでいいか」確かめる。確かめた点は、ラウンドで渡す。

成功条件: 見直し中の決まったことが、次のラウンドで問いとして出る。答えが変わったら、改めたことに残る。
反例: 見直すを受け取っても、次のラウンドに出ない。古い中身が消える。
確かめ方: 人が実物の壁打ちで確かめる。

## 収束したとき

問いの木を出し切り、未決が本人に残すものだけになったら、問いのないラウンドを出す。そのラウンドで最後の記録と完成図を渡す。画面はこれを「結果」として出す（[結果](screen.md#結果)）。
本人が「この結果で進める」で送ったら、ワークフローに戻って仕様を書く。「見直す」が届いたら、次のラウンドで問い直す。

成功条件: 収束したときに、本人が最終形と決まったことを画面で確かめてから、仕様を書く段に進む。
反例: 記録を残すためだけに問いのないラウンドを出し、本人に何をするか示さない。
確かめ方: 人が実物の壁打ちで確かめる。

## レビューのラウンド

ワークフローがレビューをして指摘が出たら、ターミナルで聞かずに、同じ議題の次のラウンドとして出す。指摘は次の 3 つに分ける。

- **直したこと**: 記録から導ける直し。直して、一覧に載せる。人には聞かない。決まったことを直したときは、前の中身を改めたことに残す。
- **人が決める問い**: [問いの仕分け](#問いの仕分け) の基準で人が決めるもの。
- **仮決め**: 同じ基準で仮決めになるもの。

議題を終えていたら、ラウンドを出すと再開する。

成功条件: レビューの指摘が、ターミナルで問いを次々に聞く形にならず、3 つに分かれた 1 つのラウンドとして画面に出る。
反例: レビューの指摘を、全部同じ重さの問いとして並べる。記録から導ける直しを、人に聞く。
確かめ方: 人が実物の壁打ちで確かめる。

## 完成図を描く

ラウンドを出すたびに、完成図を描き直す。完成図は、議題の最終形の図 1 枚。決まったことは関係する場所に短い言葉で貼り、まだ決まっていない場所は空き枠にする。

成功条件: ラウンドごとに完成図が更新され、空き枠が減っていく。
反例: 完成図が、決まったことのリストになっている。
確かめ方: 人が実物の壁打ちで確かめる。

確かめていないこと: UI のない議題でも 1 枚にまとめられるか。図が大きくなったときに重ならずに読めるか。最初の実物の壁打ちで確かめる。

## 作らないもの

- 仕様の書き方、置き場所、承認のしかた。これはワークフローの仕事。
- 今の brainstorm（ba0918・kotowari）の書き換え。それぞれのリポジトリの別作業にする。
- 毎回のブラウザ撮影とモデル評価の義務化（[説明の意味を確かめる](#説明の意味を確かめる)）。

## 見送った案

- 仮決めを LLM の判断だけで決まったことにする: 人が決めていないことが、決まったこととして残る。
- 質問を受けて問いの文を書き直す: 記録の上で、問いが途中で変わる。
- レビューの指摘をターミナルで聞く: 重さの違う問いが一度に並び、認知負荷が高い。
- 対応する内容に原則パーツを付ける方式と、本人が頼んだときだけ使う方式: 必要な構造を最小の表現で説明する判断をスキルが担う（[説明の表現を選ぶ](#説明の表現を選ぶ)）。

## 任せたこと

- 既存図と完成図のテキストの書き方の細部: 点・線・格子上の位置を書き、画面がその位置どおりに描くことは決まっている。新しい説明図の指定方法は [説明パーツの任せたこと](explanation-parts.md#任せたこと) に従う。
